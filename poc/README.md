# LiveScope: הוכחת היתכנות (שבוע 1)

סקריפטים שעונים על שלוש שאלות לפני שבונים משהו:

1. **תמלול חי:** האם Soniox מתמלל עברית מספיק טוב ומספיק מהר, תוך כדי שיחה, במיוחד מספרים, סכומים ושמות כלים?
2. **הבנה:** האם Claude מוצא מהתמלול את הכאבים והרכיבים שהייתם כותבים בעצמכם?
3. **זמן ועלות:** כמה זמן עובר מדיבור ועד עדכון מסך, וכמה עולה שיחה?

המטרה היא תמלול חי, כדי שהמערכת תרוץ במקביל לשיחה. Soniox הוא הספק הראשי, ו-Fireflies הוא הגיבוי אם Soniox לא עומד בספים למטה. ראו את סעיף 9 ב-[`docs/livescope-plan.md`](../docs/livescope-plan.md).

## התקנה

דרוש Node 22 ומעלה.

```bash
cd poc
npm install
cp .env.example .env   # ממלאים מפתחות. הקובץ .env לא נכנס לגיט
npm test               # בדיקות, בלי רשת ובלי עלות
```

| משתנה | מאיפה |
|---|---|
| `ANTHROPIC_API_KEY` | console.anthropic.com |
| `SONIOX_API_KEY` | console.soniox.com |
| `DEEPGRAM_API_KEY` | אופציונלי. Deepgram יצא מהתכנון, והסקריפט נשאר רק להשוואה |
| `LIVESCOPE_MODEL`, `LIVESCOPE_EFFORT` | אופציונלי. ברירת מחדל `claude-opus-5-5`, `low` |

## תהליך העבודה עם הקלטה אמיתית

### 0. הקלטה
- מקליטים שתי שיחות אמיתיות, **רק בהסכמת הלקוח** בתחילת השיחה.
- שמים את הקבצים ב-`recordings/` (mp3, wav, m4a). התיקייה לא נכנסת לגיט.

### 0. דף לכידה בדפדפן (תמלול חי של שיחה אמיתית)

דף שרץ על המחשב שלך, לוכד את קול הלקוח מלשונית ה-Meet או ה-Zoom, ואת קולך מהמיקרופון, ומתמלל את שניהם בזמן אמת **בנפרד**. כך תמיד ברור מי אמר מה, בלי לנחש לפי הקול.

```bash
npm run capture
```
ואז פותחים **בכרום** את `http://localhost:5173`. שים לב: הדף עובד רק בכרום, ורק על המחשב שלך.

1. פותחים את שיחת ה-Meet או ה-Zoom (בדפדפן) **בלשונית נפרדת**.
2. בדף הלכידה לוחצים "התחל". בחלון שנפתח בוחרים **לשונית (Tab)**, את לשונית השיחה, ומסמנים **"שתף גם אודיו של הלשונית"**. בלי הסימון הזה לא נקלט קול הלקוח, והדף יציג הודעה.
3. מאשרים את המיקרופון. **משתמשים באוזניות**, אחרת המיקרופון ישמע גם את הלקוח, והוא יתומלל פעמיים.
4. מדברים. הטקסט מופיע תוך כדי, ומד קטן בכל זרם מראה שהקול נקלט. טקסט אפור נטוי עדיין עשוי להשתנות.
5. "עצור" ואז "הורד JSON". קובץ ה-JSON הוא באותו פורמט שהסקריפטים קוראים, ואפשר להריץ עליו `npm run simulate`.

**מה זה לא עושה עדיין:** הדף לא שולח ל-Claude ולא מציג הערכה. הוא רק לוכד ומתמלל, וזה החלק שהיה צריך להוכיח קודם.

**איך מפרידים בין שני אנשים בשיחה מדומה**

| המצב | מה לבחור בדף | איך זה עובד |
|---|---|---|
| שני אנשים בשני מחשבים, שיחת Meet או Zoom בדפדפן | "לשונית + מיקרופון" (מומלץ) | הלשונית היא הלקוח, והמיקרופון הוא היועץ. ההפרדה מושלמת, בלי ניחוש |
| שני אנשים באותו חדר, מיקרופון אחד | "מיקרופון בלבד, עם זיהוי דוברים" | Soniox מסמן כל דובר לפי הקול. הדובר הראשון הוא היועץ, ואפשר להפוך בלחיצה |
| הקלטה קיימת של שניהם | `npm run transcribe:live -- <קובץ>` | זיהוי דוברים לפי הקול, כמו המצב השני |

זיהוי לפי הקול (שני המצבים האחרונים) פחות מדויק מהפרדה לפי זרם, במיוחד כשמדברים אחד על השני.

**בדיקה אוטומטית:** הדף נבדק בדפדפן כרום אמיתי, עם מיקרופון מדומה ושרת Soniox מדומה. לא נבדק מול Soniox אמיתי, ולא נבדק לכידת אודיו מלשונית אמיתית (מגבלה של סביבת הבדיקה). את שני אלה תבדוק אתה בריצה הראשונה.

### 1. תמלול חי (הבדיקה המרכזית)
קודם ממירים את ההקלטה לפורמט שמאפשר מדידה מדויקת (דורש ffmpeg):
```bash
ffmpeg -i recordings/call1.mp3 -ac 1 -ar 16000 -f s16le recordings/call1.pcm
```
אחר כך משדרים ל-Soniox בקצב אמיתי, כאילו זו שיחה:
```bash
# זרם אחד עם זיהוי דוברים
npm run transcribe:live -- recordings/call1.pcm --terms "StudioFlow,Meta,WhatsApp"

# שני זרמים נפרדים: לשונית הלקוח ומיקרופון היועץ (מומלץ, בלי ניחוש מי מדבר)
npm run transcribe:live -- --client recordings/client.pcm --consultant recordings/consultant.pcm
```
- התוצאה נשמרת ב-`out/<שם>/`: `transcript.soniox-live.json`, גרסת `.txt` קריאה, ו-`live-metrics.json`.
- **ההשהיה** היא הזמן בין הרגע שמילה נאמרה לרגע שהתקבלה כטקסט סופי. הסקריפט מדפיס חציון, 90% ומקסימום, וגם כמה זמן עבר עד הטוקן הראשון.
- הדובר הראשון שמדבר מסומן כיועץ. אם יצא הפוך, מוסיפים `--consultant-speaker 1` (או 0).
- אחרי הקבלה, התמלול עובר את אותו ניקוי הזיות ושגיאות זמניות מנוסות שוב.
- **לא נבדק מול Soniox אמיתי:** הלקוח נבדק רק מול שרת מדומה, לפי הדוגמה הרשמית שלהם. הריצה הראשונה עם מפתח אמיתי היא גם בדיקת החיבור.
- לגבי הדפדפן: במערכת המלאה הדפדפן מקבל מפתח זמני מהשרת (`POST /v1/auth/temporary-api-key` עם `usage_type: transcribe_websocket`, תוקף 60 שניות, לפי שרת הדוגמה שלהם), ולא את המפתח הקבוע.

### 1א. חיבור Soniox ל-Claude בזמן אמת

אין מחבר מוכן בין Soniox ל-Claude, ולא צריך כזה. Soniox מחזיר טקסט, ו-Claude מקבל טקסט. החיבור הוא הקוד שלנו:

```
הקלטה ← Soniox (תמלול חי) ← המצבר שאוסף שורות ← כל 45 שנ׳ ← Claude ← תיק אבחון ← חישוב הערכה ← מסך
```

```bash
npm run live -- recordings/call1.pcm --terms "StudioFlow" --rate 380
npm run live -- --client recordings/client.pcm --consultant recordings/consultant.pcm   # שני זרמים
```
- דרושים `SONIOX_API_KEY` ו-`ANTHROPIC_API_KEY` ב-`.env`. כל אחד מהם נוצר בקונסולה של הספק (console.soniox.com ו-console.anthropic.com).
- הסקריפט משדר בקצב אמיתי, ובכל `--window` שניות (ברירת מחדל 45) שולח ל-Claude את מה שנאמר מאז הסבב הקודם. אחרי כל סבב הוא מדפיס לחישות חדשות, רכיבים והערכה.
- אם סבב נכשל, הוא מדלג ומשאיר את התיק הקודם. הסבב הבא ממשיך.
- בסוף נשמרים `report.md` (השהיית תמלול, זמן Claude, עלות), תיק לכל סבב, והתמלול.
- נבדק רק מול שרתים מדומים של שני הספקים. הריצה הראשונה עם מפתחות אמיתיים היא גם בדיקת החיבור.

### 1ב. תמלול קובץ אחרי השיחה (השוואה ומסלול גיבוי)
```bash
npm run transcribe -- recordings/call1.mp3 --terms "StudioFlow,Meta,WhatsApp"          # Soniox
npm run transcribe -- recordings/call1.mp3 --provider both                              # גם Deepgram, אופציונלי
```
- הקובץ והתמלול נמחקים אצל Soniox אחרי העיבוד.
- קובץ התמלול הזה משמש כייחוס להשוואה בשלב 3, אחרי שמתקנים אותו ידנית.

### 2. ייחוס ידני
- מעתיקים את אחד התמלולים (מ-1ב או מהתמלול החי) ל-`out/call1/reference.json`, ומתקנים ידנית את הטקסט ואת הדוברים.
- זה האמת שמולה משווים. מספיק לתקן את השורות, בלי לגעת בזמנים.

### 3. השוואת התמלולים
```bash
npm run compare -- --ref out/call1/reference.json out/call1/transcript.soniox-live.json out/call1/transcript.soniox.json --terms "StudioFlow,וואטסאפ"
```
הדוח נשמר ב-`out/call1/compare-report.md`, ומודד את הדברים הבאים:
- **WER:** אחוז שגיאות המילים.
- **מספרים וסכומים:** כולל צורות כמו "ארבעת אלפים".
- **שמות בלועזית.**
- **שיוך דוברים.**
- **זמן עיבוד.**

### 4. סימולציה חיה עם Claude
```bash
# קודם: ספירת טוקנים בלבד (חינם), כדי לראות סדר גודל של עלות
npm run simulate -- out/call1/reference.json --dry-run

# ריצה אמיתית (עולה כסף, בערך סנטים עד דולרים בודדים לשיחה)
npm run simulate -- out/call1/reference.json
npm run simulate -- out/call1/reference.json --model claude-sonnet-5-5   # להשוואה
```
- הסקריפט מחלק את התמלול לחלונות של 45 שניות (`--window`), ושולח כל חלון ל-Claude כמו במערכת החיה.
- התוצאה נשמרת ב-`out/call1/sim/<…>/`: גרסת תיק לכל סבב, ו-`report.md` עם המדדים הבאים:
  - זמן תגובה: ממוצע, חציון ו-90%.
  - זמן משוער מדיבור ועד מסך.
  - עלות לשיחה ולשעת שיחה.
  - יציבות: האם פריטים "נעלמים" בין סבבים.
  - ציר זמן של הלחישות.
- מריצים פעם על `reference.json` (תמלול מושלם) ופעם על תמלול של ספק. כך רואים כמה טעויות התמלול פוגעות בהבנה.
- הסימולציה לא מריצה בדיקה ברקע של כלים, ולכן רכיב החיבור נשאר בטווח הזהיר.

### 5. ציון מול תיק ידני
כותבים תיק "נכון" לשיחה. הדוגמה היא `fixtures/demo-golden.json`, ומספיק למלא בו רכיבים, כאבים, מטרות, כלים ושווי חודשי. אחר כך מריצים:
```bash
npm run score -- --golden out/call1/golden.json out/call1/sim/<…>/dossier-v12.json
```
- **רכיבים:** recall ו-precision.
- **כלים:** האם זוהו.
- **שווי חודשי:** האם תואם.
- **כאבים ומטרות:** טבלה זה לצד זה, לבדיקה בעין.

## קטלוג רכיבים

הקטלוג הוא הרשימה שמתוכה Claude בוחר רכיבים. ברירת המחדל היא קטלוג ההדגמה (יועץ לעסקי שירות). אפשר להחליף אותו בקובץ משלך:

```bash
npm run simulate -- <תמלול.json> --catalog catalog/fitness-mock.json
npm run estimate -- fixtures/fitness-golden.json --catalog catalog/fitness-mock.json
```
או לקבוע לצמיתות ב-`.env`: `LIVESCOPE_CATALOG=catalog/fitness-mock.json`.

הקובץ הנוכחי, `catalog/fitness-mock.json`, נבנה מקובץ המחירים של מוצרי מאמני הכושר. קישורי התשלום לא נכללו. השדות "מתי מתאים" ו"שעות" ניסוח זמני, ודורשים אישור.

**סוגי תמחור לרכיב** (בוחרים אחד):

| שדה | משמעות | איך נספר |
|---|---|---|
| בלי שדה | מחיר לפי שעות × תעריף | בסכום, ומושפע מהתעריף |
| `fixedPrice` | מחיר קבוע חד-פעמי | בסכום, לא מושפע מהתעריף |
| `monthlyPrice` | ריטיינר חודשי | בשורה נפרדת "ריטיינר חודשי" |
| `quote: true` | המחיר נקבע בהצעה | לא בסכום, מופיע ברשימה "לפי הצעה" |

שדות נוספים: `always: true` (רכיב שנכלל בכל פרויקט, כמו אפיון ובדיקות), `hoursDerived: true` (השעות נגזרו מהמחיר ולא נמדדו, ומשמשות רק לחישוב משך), `note` (הערה שנשלחת גם ל-Claude). אם הקובץ לא תקין, הסקריפט מסביר מה לתקן.

**שיחה מדומה:** `fixtures/rehearsal-fitness.md` מתאר תסריט כיוון ותשובות צפויות לקטלוג הזה.

## איך מחליטים

הספים הם הצעה להתחלה, ואפשר לשנות אותם אחרי השיחה הראשונה.

| שאלה | סף מוצע | אם לא עובר |
|---|---|---|
| השהיה של תמלול חי (חציון) | עד 3 שניות | לבדוק חיבור ורשת. אם עדיין איטי, גיבוי: Fireflies |
| מספרים וסכומים בתמלול החי | 95% ומעלה | להוסיף מונחים (`--terms`). אם לא עוזר, גיבוי: Fireflies |
| שיוך דוברים | 95% ומעלה | לעבור לשני זרמים נפרדים |
| רכיבים: recall | 85% ומעלה | לשפר את תיאורי "מתי מתאים" בקטלוג ולהריץ שוב |
| מדיבור ועד מסך (בסימולציה) | פחות מ-60 שנ׳ | חלון קצר יותר, מאמץ נמוך יותר, או מודל מהיר יותר |
| עלות לשעת שיחה | זניחה מול מחיר אבחון (₪1,500 ומעלה) | — |

**הגיבוי:** Fireflies נבדק רק אם אחד משלושת הספים הראשונים נכשל. הוא נכנס מאחורי אותו ממשק תמלול, ושאר המערכת לא משתנה.

## מבנה

```
src/core/        קטלוג, חישוב הערכה, סכמת תיק, השוואת תמלולים, חלונות זמן
src/transcribe/  Soniox (חי וקובץ), Deepgram (אופציונלי), ניקוי הזיות, ניסיון חוזר, ופורמט תמלול אחיד
src/extract/     הפרומפט והקריאה ל-Claude (פלט מובנה, fallback, מדידת עלות)
src/cli/         הפקודות שלמעלה
test/            בדיקות (npm test). הקריאה ל-Claude נבדקת מול שרת מדומה
fixtures/        שיחת ההדגמה: תמלול, תמלול עם טעויות, ותיק ידני
```

הקוד ב-`src/core/` הוא הבסיס לחבילת `shared` במערכת המלאה.
